## Local SQLite runtime

The authoritative runtime database is `data/techtree.sqlite3` (absolute project path: `/Users/prakashnarayanan/Documents/2026_Takeoff/data/techtree.sqlite3`). Python's standard-library `sqlite3` and a small HTTP server provide the backend; there is no ORM, external database service or extra package. Start with `npm start`, bound to `127.0.0.1:4173`. The frontend obtains its collection, evidence, tree, desk and activity from `/api/bootstrap` and the database-backed API. JSON files under `web/data/` are seed/backup inputs only; `/data/` URLs are not a runtime fallback and seeds are excluded from the built frontend.

On first initialization, a transaction imports 660 milestones, 66 fields, 444 tree relationships, two preserved collection-layer relationship proposals, 42 branches, nine evidence records and ten associations. Duplicate targets and graph references use foreign keys. Structured scientific payloads preserve all wording, scope, rationale and provenance; relational columns provide identity and integrity. Original history and the already-existing tree-first history entry become revision rows. Initialization is idempotent: an existing initialized database is not refreshed from seeds on restart. Regenerating a JSON seed does not update runtime SQLite or overwrite later saved data.

Schema tables: `fields`, `milestones`, `relationships`, `relationship_evidence`, `branches`, `branch_nodes`, `connection_reviews`, `evidence`, `associations`, `submissions`, `review_activity`, `revisions`, `migration_snapshots`, `migration_conflicts`, `legacy_records`, plus document metadata and initialization settings. Core collections are reconstructed from these tables. No browser API edits scientific content or promotes a suggestion to verified evidence. Submissions are created individually; dismissals require the current record version, returning HTTP 409 for a stale update. Writes use transactions, foreign keys, a busy timeout and SQLite WAL. Browser requests must be same-origin JSON; the server binds only to loopback.

### Existing browser saves

On opening the website, the browser sends any `techtree-evidence-desk-v2` and `techtree-state-v1` raw saves to `/api/migrate-browser`. The raw strings are preserved verbatim in SQLite and are never cleared or replaced in localStorage. Snapshot hashes and original record identities prevent repeated reloads/imports from creating duplicate submissions or audit events. Current desk submissions are validated and imported as unverified pending/dismissed suggestions. Earlier prototype proposals, reviews and revisions are archived as unverified legacy history, never replayed into scientific data.

Conflicting identities or states are retained for inspection rather than overwriting either copy. Malformed or unknown structures are preserved as raw snapshots with issues. **Research desk** shows the migration report and conflicts; its full-data export and SQLite backup include raw saves and conflicting records. A browser which does not contain the old saves cannot migrate another browser's localStorage. Open the original browser at the same origin (for example, `http://localhost:4173`, not `127.0.0.1`) to trigger import. Migration was tested with synthetic saves in a separate temporary database; no preexisting saves were found in the inspected preview browser, so migration of the user's viewing-browser data is not independently confirmed.

### Run, back up and restore

- Start: `npm start`.
- Test: `npm test` (JavaScript graph/content checks plus disposable-database Python/API tests).
- Build: `npm run build` (frontend assets; the local backend is still required).
- Safe backup while running: `npm run backup`, or **Research desk → Back up SQLite**. These use SQLite's backup API, not a raw copy of a live WAL database. CLI backups are placed under `data/backups/` by default; a destination can be supplied with `python3 scripts/backup_db.py /absolute/path/backup.sqlite3`.
- JSON export: **Research desk → Export all saved data**. Original source files and seed inputs also remain on disk unchanged.
- Restore safely: stop the local server, retain the existing database and any accompanying `-wal`/`-shm` files as a backup, then place a consistent SQLite backup at `data/techtree.sqlite3`. Restart. To inspect a backup without replacing anything, run `python3 scripts/serve.py --db /absolute/path/backup.sqlite3 --port 4174`.

Database files, WAL sidecars and private backup files are ignored by Git. Tests never use the real database and leave no synthetic submissions there. SQLite is local storage, not a shared hosted service or deployment.

## Reproducing the committed reviewed state

`research/reviewed-project-state.json` is a curated, hash-checked export of the scientific records, graph revisions, complete source-audit history and source-role assignments. It excludes local settings, browser saves, user submissions and runtime database files. The original source documents, seed inputs, authored review batches and controller receipts are also retained in the repository.

On a fresh checkout, restore into a **new** database filename with `python3 scripts/restore_project_state.py --db data/restored.sqlite3`, then inspect it using `python3 scripts/serve.py --db data/restored.sqlite3 --port 4174`. The restore refuses existing paths, verifies the original corpus and snapshot hash, and checks schema, foreign keys and database integrity. Starting the app without this restore creates only the ordinary seed state; it does not silently import the completed audit.

Generated `dist/`, local SQLite/WAL files, private backups, dependencies and caches remain outside Git. The build regenerates `dist/`; consistent SQLite backups remain the operational backup mechanism. The committed scientific snapshot is not a backup of private browser or submission data.
